# Words in images: cost, choices, and what the phone must measure (lane L3, 2026-10-29)

Goal: words in screenshots, receipts and documents become searchable ("Uber receipt", names, numbers, "@handle") at a
bounded heat cost. Indexing was already thermal-bound on the phone (30k proof §2: `serious` 62 % of the time, 46
pauses), so cost per image and which images are read are the decisions that matter.

Evidence files (all in `docs/investigations/evidence/2026-10-29-ocr/`):

| File | What |
|---|---|
| `mac-ocr-bench.swift` | the OCR bench (compile with `swiftc -O`, run on `artifacts/seed`) |
| `mac-ocr.json` | method, host and the summary per setting (text images vs photos) |
| `mac-ocr-images.jsonl` | one line per image: size, reference word count, ms and recall per setting |
| `keyword-coverage-bench.swift`, `keyword-coverage-mac.json` | `keywordCoverage` latency at the founder's scale (synthetic text) |

## 1. Cost per image on the Mac (measured)

Host: Apple M1 Pro, macOS 26.6.2. Inputs: the synthetic seed set (`scripts/make_seed_media.py`): 12 screenshots
(1170 × 2532), 6 receipts (1000 × 2400), 2 document photos, 8 memes, and 4 photos without text. No private photos.
Each setting: median of 5 runs after a warm-up, one image at a time, image already decoded and resized (so the time
is Vision only). Recall = share of the reference terms (`.accurate` + language correction on the full image) that a
setting found; terms are tokenized like search (lowercase, diacritics folded, split on non-alphanumerics, ≥ 2 chars).
One variable at a time: image long side (300, 960, 1600) and recognition level; language correction at 960 only.
The Mac was not idle (other lanes were building in parallel), so single timings are noisy; medians are reported.

All 28 images with text (`mac-ocr.json` `summary`):

| Setting | Median ms | Mean ms | Mean recall |
|---|---|---|---|
| `.fast`, 300 px | 10 | 13 | 0.12 |
| `.fast`, 960 px | 16 | 27 | 0.20 |
| `.fast`, 1600 px | 17 | 27 | 0.21 |
| `.accurate`, 300 px (Roll's analysis thumbnail) | 201 | 241 | **0.30** |
| **`.accurate`, 960 px** (chosen) | **264** | 317 | **0.93** |
| `.accurate`, 960 px, language correction | 351 | 405 | 0.94 |
| `.accurate`, 1600 px | 258 | 313 | 0.93 |

By kind (`.accurate`, from `mac-ocr-images.jsonl`): screenshots 350 ms median, recall 0.99 at 960 px and 0.11 at
300 px; receipts 238 ms, 0.99 at 960 px and 0.05 at 300 px; memes 233 ms, 0.92 (0.86 at 300 px: big text). The 4
photos without text still cost 160–220 ms each at `.accurate`: reading an image costs the same whether or not it has
words, which is why only gated images are read. p90 for text images at 960 px: 506 ms.

What follows from it:

- **Size decides more than anything.** Roll analyses images at 300 px (`IndexerConfig.thumbnailSide`; the ≤ 960 px of
  v8 is history). At 300 px a screenshot's body text is 4–5 px tall and `.accurate` finds 4–16 % of its words. So
  OCR can't run on the image the signal pass already has; it needs its own 960 px image. 1600 px reads no more.
- **`.fast` is not an option**: it found almost nothing on screenshots and receipts (0–4 %) at any size.
- **Language correction off**: +1.3 points of recall for a third more time, and it rewrites exactly what people search
  for literally (names, handles, codes, amounts). DigUp keeps it on (desktop, plenty of power); here heat is the
  budget.
- Defaults: `TextRecognizer(level: .accurate, languageCorrection: false)`, `TextPassConfig.side = 960`.

## 2. Design

**The gate** (`TextGate.wantsText`, Store, pure and tested; the same rule in SQL for the candidate query, with a test
that both agree on every combination): photos (`mediaType = 1`) that are screenshots (`subtypes & 4`) or that Vision's
aesthetics request marked `isUtility`. `isUtility` comes from the signal pass (`VisionBatch`), so an image is read only
once `signalsDone = 1`. Videos are never read.

**A pass of its own, not inside the signal pass.** The brief asked for OCR inside the signal pass plus a backfill.
I made it one text pass (`TextIndexer`) for both, run after the signal pass, because:

1. it needs a second, larger image anyway (§1), so nothing is shared with the signal pass but the asset id;
2. ~264 ms per gated image (Mac) against ~54 ms per asset for the whole signal + embedding pass on the phone (18.5
   items/s, proof §2): inline, it would slow the first index and the onboarding taste scan (`run(limit: 500)`, the
   newest 500, where screenshots cluster) exactly while the person waits, and add heat to a pass that is already
   thermal-bound;
3. `Indexer.swift` is 46.8 KB; any edit is blocked by the 5k-token pre-commit hook, and it didn't need one: deletion
   and edit cleanup are Store triggers (below), so the Indexer is untouched.

New images get read by the next text pass, which the app starts when indexing drains (wiring in §5) and the background
task runs after its index run. Pre-v10 rows need no flag: the candidate query is "gated, analysed, no text at this
revision", which covers them.

**Throttling.** One image at a time; the pass waits while the device is `.fair` or warmer (`ThermalGate(pausesAt:
.fair)`, a new parameter; the Indexer keeps `.serious`). Cancellation follows the Indexer's rules: the image in flight
is dropped, everything read before it is committed in a task of its own. Commits every 20 images. It writes only the
text tables: no signals, flags or vectors, and never embeds.

**Images that can't be read.** The 960 px image is asked for with the network off. A full image (or the original, if
smaller) is read; a local preview is read only if it is at least 90 % of 960 px. Otherwise the row is recorded unread
(`side = NULL`, empty text): local passes skip it, a pass with `allowNetwork` (Wi-Fi, the app decides) tries again
and may download. Failed loads and Vision errors are recorded the same way.

## 3. Schema v10 and the keyword index

- `assetText(id INTEGER PK, assetId UNIQUE → asset ON DELETE CASCADE, text, terms, revision, side, readAt)`: the
  text as read (lines joined by newlines), its unique search terms, the reader revision
  (`vision-text-accurate-1@960`: settings or image size change → everything is read again), the long side read.
- `assetTextFts`: FTS5 over `terms`, external content (`assetText`), kept in step by triggers.
  Tokenizer `porter unicode61 remove_diacritics 2 categories 'L* N* Co M*'`.
- Triggers on `asset`: text goes when an asset is marked deleted, or edited (`signalsDone` 1 → 0, which only
  `resetForContentChange` does), whichever writer did it (sync, change observer, `recordApplied` after a commit).
  `DELETE FROM asset` cascades. So the Indexer needed no change for "deleted assets drop their text".
- `asset_textGated`: a partial index with the gate's WHERE clause, so the candidate query and its count stay cheap.
- The DEBUG UI-test reset skips `assetTextFts*` (SQLite refuses writes to FTS shadow tables; the triggers empty the
  index when `asset` and `assetText` are emptied).

**Tokenizing.** Indexed terms are `TextTerms.terms(text)`: lowercase, diacritics folded (`.diacriticInsensitive`),
split on non-alphanumerics, ≥ 2 characters: the rule L2's `SearchTerms.terms` applies to queries. The index stores
already-folded terms, so a query term and an indexed word meet even where SQLite's folding and Foundation's differ.
Marks count as letters in the tokenizer, as in Swift's `alphanumerics`, so the two split words the same way.

**Porter stemming: on.** Typed queries are mostly English nouns and verbs whose forms differ from the screen's
("receipts" vs "receipt", "printing" vs "printed"); without stemming those are misses, and the prefix fallback can't
cover them (it only applies to a term found nowhere whole). The cost: Porter is English-only (Spanish words are
stemmed by English rules, but the same way on both sides, so matches still meet) and it conflates a few unrelated
words ("general"/"generous"). Keyword coverage is a bonus on top of meaning search, so a little over-matching is
cheaper than missing plurals. Numbers, names and handles are not affected.

**`keywordCoverage(terms:) -> [String: Double]`** (the L2 contract): asset id → share of distinct terms found in that
asset's text, live assets only. A term of three or more characters that no live text has as a whole word matches as
a prefix ("grok" → "Grokipedia"), like DigUp; a term found whole stays whole ("cat" doesn't bring in "category").
Caps: the best 1,000 matches per term by bm25 and the first 16 terms, so at most 16,000 entries (in practice no more
than the number of images with text).

Latency on the Mac (`keyword-coverage-mac.json`; 30,000 assets, 6,300 with 63 terms each, debug build, noisy):
a rare term 0.7–0.9 ms, a term in every text (capped at 1,000) 8.7–21.5 ms, 3 terms 9–12 ms, 6 terms 20–24 ms,
prefix fallback 0.5 ms. The database with 6,300 texts was 10.3 MB in total (asset rows included).

## 4. The phone: estimate (not measured)

**This section is an estimate.** Nothing here ran on the iPhone 13 Pro Max.

- Gated images on the founder's library: 2,532 screenshots + 3,821 `isUtility` (plan, from the 30k proof's store);
  the overlap is unknown, so **at most ~6.35k**.
- Per image: assume Vision `.accurate` on the A15 takes 1–2× the M1 Pro median, **~0.26–0.53 s**, plus the
  960 px image request (unmeasured; assume 20–50 ms when local).
- Busy time for the whole backfill: 6,350 × 0.29–0.58 s ≈ **31–61 min**, before thermal pauses.
- Wall time depends on heat. The pass pauses from `.fair`; during the proof's indexing the phone was `.fair` or
  `.serious` 93 % of the time, so right after a full index the foreground pass would mostly wait. Expect the backfill
  to happen in background runs (charging, `BGProcessingTask`) over one or more nights.
- How much is readable offline is the largest unknown. The 2026-10-24 device probe got 960 px locally for only
  4–15 % of 400 sampled assets on an Optimize Storage library (300 px: 100 %). If screenshots behave the same, a
  local pass records most gated images unread and the words come only from Wi-Fi passes that download.
- `keywordCoverage` on the phone: assume 2–3× the Mac, so up to ~60 ms for six common terms; tight against L2's
  100 ms typed-query budget if the vector search is slow too. The per-term cap is the knob.

## 5. What the phone run must measure

Run with `-QAMetrics` (or a QA hook at integration) on the proof build's data:

1. **Readable offline**: a local `textIndexer.run(limit: 300)`: `TextReport.read` vs `unread` (share of gated
   images with a local 960 px image), split screenshots vs `isUtility`.
2. **ms per image**: wall time of that run ÷ images read, and Vision alone vs the image request (two timestamps per
   image in a DEBUG log).
3. **Heat**: thermal state over a 20-minute pass, plugged in and unplugged; `TextReport.thermalPolls` × 5 s =
   paused time. Decide whether `.fair` is the right ceiling.
4. **Gated count and overlap**: `textCandidateCount` before the first pass; screenshots that are also `isUtility`.
5. **Network pass**: `run(allowNetwork: true, limit: 200)` on Wi-Fi: images read per minute, data downloaded.
6. **Words found on real screenshots**: the founder checks ~20 gated images against what is visible (private: notes
   stay out of the repo).
7. **`keywordCoverage` latency** on the device with the real texts: 1, 3 and 6 terms, common and rare.
8. **Database growth**: bytes of `assetText` + `assetTextFts` after the backfill.

## 6. App wiring needed (not done here; App files belong to integration)

- `AppModel`: build `TextIndexer(library: <the PhotoLibrary>, reader: TextRecognizer(), repo: repositories)` next to
  the Indexer.
- `RollApp.init`: `IndexScheduler.register(indexer: { indexer }, text: { textIndexer })` (the `text:` parameter
  defaults to none).
- `scenePhase == .background`: `IndexScheduler.appDidEnterBackground(indexer:text:)`: it stops the text pass (which
  commits what it read) and schedules a background run while words are unread.
- `startIndexing()`: once the loop has drained (where `startChecks()` starts), run `textIndexer.run()` (local only) at
  utility priority; cancel it (`await textIndexer.cancel()`) wherever the Indexer is cancelled or a taste scan starts.
- The iCloud upgrade pass (Wi-Fi + charging): follow it with `textIndexer.run(allowNetwork: true)`.
- Typed search (L2): `keywordCoverage: { try await repositories.keywordCoverage(terms: $0) }`.
- AGENTS.md map: Store schema is v1–v10; Signals has `TextRecognizer`; Indexer has `TextIndexer`.
