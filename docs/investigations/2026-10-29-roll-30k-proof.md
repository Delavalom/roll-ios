The founder's four questions (embeddinggemma-coreml `docs/investigations/2026-10-28-HANDOFF.md`, Job 4), answered with
measurements from one Debug build of Roll on the founder's iPhone. Every number below cites its evidence file in
`evidence/2026-10-29-roll-30k-proof/` (identifier-free extracts) or the raw log.

| Question | Answer | Evidence |
|---|---|---|
| 1. Does it work as specified? | Yes, end to end: download stand-in → "Preparing search" (9/9) → full index → Home categories → search. Two quality problems (below). | all files |
| 2. Search ~30,000 photos within milliseconds? | **No: ~300–320 ms** per search over all 29,681 vectors (~100–105 ms with a pre-filter). Works, but not "milliseconds". The model is not the cost (cached query vectors; 6.7 ms when not cached, s6). | `session2-search.jsonl`, `summary.json` `search_ms` |
| 3. Analyse ~30,000 photos and group them into categories? | **Yes: 29,685 assets in 75.8 min, 0 failed**, 29,681 with vectors and signals. Categories produced; Similar shots and Blurry look too loose. | `summary.json` `index_full`, `session1-final-home-and-store.json` |
| 4. Show the results screen? | Home shows the categories and headline. Screenshots of Home, a big Similar group, Blurry and Receipts are with the founder (not in the repo: they show photos). | founder's phone |

## Setup

- Phone: iPhone 13 Pro Max (`iPhone14,3`), iOS 27.0.1, 6 cores, 5.9 GB RAM, jetsam limit 3,072 MB. Photos access full.
  On USB, charging, battery full throughout. True free space at launch 11.1 GB
  (`~/egcm-evidence-raw/2026-10-29/roll-proof/disk-pre.txt`).
- Library: 29,685 assets: 24,495 images, 5,190 videos, 2,532 screenshots, 2,169 Live Photos, 24 user albums
  (`summary.json` `library_totals`). About 99.9 % of the bytes are in iCloud (Optimize Storage).
- Build: roll-ios `feat/per-budget-packages` (Job 3, e7c852f) plus the QA tools of this proof, Debug. The model is
  not published yet, so the b70 package from embeddinggemma-coreml s6 (`files.json` 99a7d340…, the certified one) was
  bundled through the Debug-only `artifacts/local-model/` step and loaded by `GemmaEmbedder.developerSource`
  (`.file`, copied into the package's store). Release builds never bundle it.
- Launch 1 (09:10:27 AST): `-QAMetrics -QASearchBench -UITestResetState -UITestSkipPaywall` (Roll's database, index and
  onboarding reset; paywall skipped). The founder went through onboarding. Launch 2 (11:19:13): the fixed search
  benchmark build installed over it (data kept), `-QAMetrics -QASearchBench`.
- Raw log: `~/egcm-evidence-raw/2026-10-29/roll-proof/qa/metrics.jsonl` (Roll's `Documents/qa`, appended across
  sessions; this proof is `t >= 1793279427`). The extracts here are made from it by `evidence/2026-10-29-roll-30k-proof/extract.py`.

## 1. Preparing search (Job 3 on the device)

- "Preparing search, first time only" ran 9 functions one at a time: **17.2 min** (up 15 s → 1,044 s), steps at
  15, 73, 133, 189, 247, 376, 504, 788, 918 s: text functions ~1 min each, image functions 2–4.7 min
  (`summary.json` `prepare`, `session1-model-and-runs.jsonl`).
- Peak memory while preparing **1,381 MB** (under the 2,100 MB cold-compile gate of ADR-0009). The phone was
  thermally `serious` from 71 s on (`session1-thermal.jsonl`).
- The onboarding taste scan (500 newest, signals only) ran meanwhile: 500 analysed, 0 failed, 576 s (mostly thermal
  pause).

## 3. Search

`QASearchBench` ran each embedding-ranked preset 5 times through `SwipefileEngine.candidates` (20 results), the
app's own search path (`session2-search.jsonl`):

| Preset | Scope | Attempts (ms) | Median of attempts 2–5 |
|---|---|---|---|
| Receipts & documents | all embedded assets | 52,526 · 720 · 318 · 312 · 319 | **318 ms** |
| Private | all | 324 · 315 · 309 · 310 · 314 | **312 ms** |
| Memes | images | 319 · 296 · 298 · 301 · 297 | **297 ms** |
| Screenshots | screenshots only | 112 · 102 · 105 · 103 · 102 | **103 ms** |
| Blurry | blur/aesthetic filter | 115 · 105 · 106 · 105 · 105 | **105 ms** |

- The 52.5 s first search is the text function compiling: the fix build was installed over the app with the same
  build number, so `prepareIfNeeded` skipped (marker matched) while the install had moved the container (new cache
  key). A real install or update has a new build number and prepares first. Dev-only, but see the fixes handoff.
- Prompt vectors are cached per swipefile (`SwipefileEngine.promptVectors`), so the warm times are almost all Roll's
  own ranking path, not the model. Breakdown and fix: `2026-10-29-fixes-HANDOFF.md`.

## 4. Categories (Home, final)

From `session1-final-home-and-store.json` (`home`):

| Category | Count | About | Looks right? |
|---|---|---|---|
| Screenshots | 2,532 | 2.50 GB | yes (matches PhotoKit's 2,532) |
| Duplicates | 722 extra (593 groups, 1,315 members, largest 9) | 3.91 GB | plausible |
| Similar shots | 10,225 extra (2,835 groups, 13,060 members, **largest 175**) | 44.99 GB | **no**: 44 % of the library in groups, one group of 175 |
| Blurry | 2,877 | 40.27 GB | **suspicious**: 14 MB average, so likely videos; needs the founder's look |
| Big videos | 318 | 46.49 GB | yes (squish savings 0: none on the device) |

- Library 170.5 GB, of which 23 MB on the device; freeable 87.25 GB, of which **11.5 MB on this iPhone** and 87.24 GB in
  iCloud. Home's headline is the on-device figure (as designed after the 10-23 QA).
- `byUTI` shows 19,512 assets as `unknown` type (`store_stats`): the file-type lookup didn't run for most rows.
  Not a gate here, but Squish's estimates depend on it. Listed in the handoff. **Correction (L5):** the lookup did
  cover every row it is meant to; the NULL rows are videos, small photos and excluded kinds that never need a type
  (`2026-10-29-small-fixes.md` §2).

## What this proves, and what it doesn't

- Proven: the product pipeline works on a real 30k library on a 2021 iPhone: model install, one-at-a-time compile,
  full analysis with 0 failures, categories, search over everything.
- Not good enough yet: search latency (~0.3 s), Similar shots and Blurry quality, thermal-bound indexing time.
  `2026-10-29-fixes-HANDOFF.md` has the measurements, the code paths and the questions for the next session.
- Not measured: an unplugged run, battery drain, a newer phone (b280), a published-model download.
