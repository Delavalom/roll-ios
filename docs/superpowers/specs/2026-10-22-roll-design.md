# Roll (codename): on-device AI photo cleanup. Design

**Date:** 2026-10-22
**Status:** approved through the founder's answers to the upfront question list. Separate spec review waived.
**Repo:** `Delavalom/roll-ios`, private.
**Bundle ID:** `com.delavalom.roll`.
**Store name:** chosen when the App Store Connect record is created. It must be unique, so "Sift", "Cull", "Pile", "Kept" and "Sorta" are out (all taken by photo cleaners, checked 2026-10-22). Run an ASO keyword check first.

## 1. Product

People with tens of thousands of photos use Roll to find what to delete or shrink. Users describe a pile in plain words ("memes", "screenshots of tweets", "blurry", "photos of my ex", "private stuff"). Roll finds it with EmbeddingGemma 2 running fully on-device, and the user swipes through it. **Nothing about a photo ever leaves the phone.** That promise is literal: the only network calls are the model download (Hugging Face) and RevenueCat.

### What's in v1

1. **Swipefiles:** user-defined or preset piles, each with a swipe review that learns from every swipe.
2. **Cleanup home:** "You can free about X GB", split into Duplicates, Similar shots, Screenshots, Blurry, Big videos and Swipefiles.
3. **Squish:** compress large videos (HEVC) and photos (HEIC) and replace the originals. Shown only when the estimated saving is at least 30%.
4. **Device monitor:** storage, RAM, CPU, thermal state and battery for the whole device, live and read-only.
5. **Pro subscription** through RevenueCat.

**Not in v1:** contacts or calendar cleanup, cloud anything, iPad layout, widgets, localization (English only), analytics SDKs.

## 2. Platform

- Native Swift 6, SwiftUI, iOS 18.0 minimum, iPhone only.
- Project generated by **XcodeGen** (`project.yml` in git, `.xcodeproj` gitignored), so agents never hand-merge pbxproj files.
- Dependencies (SwiftPM):
  - `EmbeddingGemma` + `EmbeddingIndex`: local path `../embeddinggemma-coreml/swift` during development, switched to the tagged version at release;
  - `GRDB` (SQLite);
  - `RevenueCat` (`purchases-ios`).

## 3. Architecture

```
RollApp (SwiftUI, @Observable view models)
├── Features/
│   ├── Onboarding/   # value, Photos permission, taste scan, paywall
│   ├── Home/         # cleanup categories with sizes
│   ├── Swipefiles/   # list, create, SwipeReview (card stack), CommitSheet
│   ├── Duplicates/   # group review: keep the best one
│   ├── Squish/       # compression candidates, progress, results
│   ├── Monitor/      # live gauges + Swift Charts
│   └── Paywall/
└── Core/ (each a separate SwiftPM target in Packages/RollCore, testable without the app)
    ├── Library/      # PhotoKit access, change observer, asset metadata, size estimates
    ├── Indexer/      # pipeline: thumbnail → embed + Vision signals → store; scheduling, thermal pause
    ├── Signals/      # Vision: feature print, aesthetics/isUtility, blur, screenshot subtype, sensitive content
    ├── Store/        # GRDB schema + repositories; EmbeddingIndex file
    ├── Ranking/      # swipefile scoring + per-swipefile logistic classifier
    ├── Dedupe/       # time-window grouping + feature print + embedding clustering
    ├── Squish/       # HEVC/HEIC re-encode, metadata preservation, replace flow
    ├── Monitor/      # Mach host stats, storage, thermal, battery samplers
    ├── Entitlements/ # free quota policy, ProStatus protocol (the RevenueCat wrapper lives in the app target)
    └── Embedding/    # `Embedder` protocol; GemmaEmbedder (real) + StubEmbedder (tests/previews)
```

**Data flow:** PhotoKit → Indexer → (Embedder, Signals) → Store. Swipefile / Dedupe / Squish read the Store and produce candidate lists. The user swipes, and decisions are queued in the Store. The CommitSheet then runs the PhotoKit change (delete, add to album, replace). iOS shows its own delete confirmation, and nothing destructive happens without it.

## 4. Indexing

- **Enumerate:** all images and videos via `PHAsset.fetchAssets`, newest first, so the taste scan shows recent photos quickly.
- **Per-asset input:** a local thumbnail through `PHImageManager` at the EmbeddingGemma bucket size, with `isNetworkAccessAllowed = false`. iCloud-only assets without a local thumbnail are marked `cloudOnly` and retried later with network allowed, on Wi-Fi only.
- **Videos:** one frame at 10% of the duration is embedded as an image.
- **Per-asset outputs:**
  - EmbeddingGemma vector (256 dims) → `EmbeddingIndex`.
  - Vision `FeaturePrint` → stored (for dedupe).
  - `CalculateImageAestheticsScoresRequest`: `overallScore` and `isUtility`.
  - Blur score: variance of the Laplacian on a 256-px grayscale thumbnail using vImage.
  - `mediaSubtypes` (screenshot, screen recording, live photo, burst id), pixel size, duration, creation date, favorite, estimated bytes (§7).
  - Sensitive flag: `SCSensitivityAnalyzer`, only when its policy isn't `.disabled`. Otherwise it stays nil, and the Private preset uses the embedding only.
- **Scheduling:**
  - Runs in the foreground with a progress UI.
  - Continues in a `BGProcessingTask` that requires external power.
  - Pauses when `ProcessInfo.thermalState >= .serious` and resumes at `.fair`.
  - Batches commit every 200 assets so progress survives being killed.
  - New photos are picked up incrementally through `PHPhotoLibraryChangeObserver`.
- **Re-index:** if `EmbeddingGemma.modelRevision` changes, vectors are re-embedded (the index throws `.revisionMismatch`). Vision signals are kept.

## 5. Swipefiles

- **Model:** `Swipefile { id, name, prompts: [String], positiveExamples: [assetId], kind: preset|custom, defaultAction: delete|album(name)|squish, classifier: (w: [Float] 256, b: Float)?, createdAt }`.
- **Score before training:** `max over prompts of cos(embed(query: prompt), v)`, plus `0.5 · mean cos(v, positive example vectors)` if examples exist. Presets add their signal (below).
- **Learning:** once a swipefile has ≥ 8 swipes with at least 2 of each kind, train an L2-regularized logistic regression on the 256-d vectors:
  - positives = swiped "belongs" (left / action, and up / album), negatives = swiped "keep" (right). Album stays a positive because the classifier learns "belongs in this pile", not "should be deleted"; what happens to each card is its verdict's business;
  - the prompt vector is added as a pseudo-positive with weight 2;
  - **class-balanced weights:** each class's total weight is 0.5, and the prompt pseudo-positives keep their 2× weight relative to the other positives. Users mostly keep, so unbalanced weights would push every probability under 0.5;
  - plain gradient descent with Accelerate, about 200 iterations, under 50 ms;
  - score = classifier probability, retrained after every 5 new swipes. Undoing a swipe on a trained pile makes the next swipe retrain, so the undone decision leaves the model. Overlapping retrains are skipped, and swipes made during a retrain still count toward the next one;
  - the classifier stores the embedder revision it was trained on. A classifier from another revision is ignored, and resetting the index (model change) drops every classifier.
- **Retrieval:** one SQL query selects the pool: live, embedded, passing the preset's filter, not yet decided in this swipefile, and not already on screen. One `dotAll` call scores the pool against all prompts (plus the mean example vector) or against the classifier weights. Only assets that have a vector are scored.
  - Before training, cards need a score of at least 0.2 (cosine scale).
  - After training, retrieval is **rank-based**: the top 20 of the pool by score. Only near-certain non-matches (probability < 0.05) are dropped. Cards under 0.5 are flagged *low confidence* for the UI. An absolute 0.5 floor emptied piles while real matches remained, and the pile could never recover because only a swipe retrains.
  - **"Looks done":** when the last 10 swipes in a swipefile were all keep, the UI offers "Looks done — finish?". This is a hint only and never hides candidates.
- **Presets:**

  | Preset | Candidates | Ranking |
  |---|---|---|
  | Screenshots | `mediaSubtypes.photoScreenshot` (exact) | embedding, so "screenshots of tweets" can narrow it |
  | Blurry | blur score below a threshold or `overallScore < -0.3` | blur score |
  | Memes | prompts "a meme with caption text", "reaction image", "internet meme" | embedding |
  | Receipts & documents | `isUtility` OR prompts "a receipt", "a document photo", "a whiteboard" | embedding |
  | Private | sensitive flag if available, plus prompts | embedding. The preset is hidden behind Face ID (`LocalAuthentication`) |
  | Big videos | duration × estimated bitrate | estimated bytes. Default action: squish |

- **Swipe review:**
  - A card stack showing 20 candidates at a time (see Retrieval: a 0.2 cosine floor before training, rank-based after, with weak matches flagged). A refill excludes the cards already on screen.
  - Left = the swipefile's action, right = keep, up = add to an album, tap = full screen. Unlimited undo inside the session.
  - A footer shows "N queued · about X GB". **Review & apply** opens the CommitSheet.
- **Free quota:** scans, swipefiles, swipes and the monitor are free. *Applying* deletes, album moves and squishes is free for the first 50 items (lifetime, counted in the Store), then needs Pro.

## 6. Duplicates and similar shots

- **Grouping:** sort by creation date, then compare each asset with its next 24 neighbors that were created within 120 s (a cap, so a burst with one timestamp stays linear). Link a pair when the FeaturePrint distance is under 0.35 (similar) or the 32×32 thumbnail hash differs by at most 4 bits (exact or near-exact duplicate). Assets the library already put in the same burst are linked without comparison. Then take connected components.
- **Cross-time exact duplicates** (saved twice, re-downloaded) come from the same perceptual hash across the whole library. Blank or saturated hashes (0, all ones, 4 or fewer or 60 or more bits set) are ignored, and a hash shared by more than 8 assets (a recurring screen or template) links only pairs whose feature prints are also close.
- **Default keeper:** favorite > highest aesthetics score > largest pixel count > newest. The user can change it, and the others are queued for deletion.

## 7. Size estimates

PhotoKit has no public API for file size. We don't use KVC on `PHAssetResource`: it's undocumented and an App Review risk (ADR-0001).

- **Estimates:** photos = pixel count × 0.35 B/px (HEIC), × 0.9 (JPEG) or × 1.6 (PNG), by UTI (screenshots at most 0.40). Types are looked up lazily, only for photos of at least 1.875 MP (3 MB at the PNG rate: anything smaller can't be a Squish candidate); until then a photo counts at the HEIC rate, and one below that size, never looked up, at 0.6 (mostly JPEGs saved from messaging apps); videos = duration × a bitrate table keyed by resolution (short side) and frame rate (60 for high-frame-rate clips, else 30).
- The UI always says "about".
- When Squish runs, it measures the real bytes, and the post-squish number shown is exact.

## 8. Squish (compression)

- **Candidates:** videos estimated over 50 MB, or a bitrate over 1.5× the HEVC target (resolution × frame rate × 0.07 bits per pixel, between 1.5 and 25 Mbps). Photos that are JPEG/PNG and over 3 MB. Only items expected to save at least 30% are offered (a constant shared with the UI). Copies Roll made itself are never offered. Once the format probe has read a local video it also measures it (codec, file size, frame rate; Store table `videoProbe`, kept while the asset is unchanged), and the plan uses the real size and frame rate instead of the estimate. An HEVC video kept at its own size is planned at 0.10 bits per pixel instead of 0.07 (re-encoding HEVC competes with the encoder that made it), so it's offered only above about 0.143 bits per pixel (8.9 Mbps at 1080p30): camera HEVC at 1080p and below, and Roll's own copies after a reinstall, aren't offered and are listed under "Not squishable yet" as "Already compact (HEVC)" ("Already compact" for other codecs). With measured facts the bitrate test uses the target at the 1080p cap, so 4K files that downscale stay offered. Before the probe a video is offered on its estimate but not selected.
- **Formats (v1):** photos must be JPEG or PNG (HEIC is already compressed; DNG, ProRAW and the rest are refused). Videos in ProRes, Apple Log or Dolby Vision are refused (Dolby Vision is what an iPhone records by default in HDR, so HDR-by-default videos are skipped in v1).
- **Videos:** `AVAssetExportSession` with an HEVC preset at the same resolution, capped at 1080p unless the user picks "keep 4K"; the downscale is shown in the plan ("1080p (from 4K)").
- **Photos:** ImageIO re-encodes to HEIC at quality 0.8, keeping the HDR gain map and other auxiliary data. Every EXIF, GPS, TIFF and IPTC key in the source must survive (IPTC `DateCreated`/`TimeCreated` may fold into EXIF when the EXIF dates match), plus orientation and colour model.
- **Kept on the new asset:** creation date, location, favorite and hidden state, and album membership in every regular user album (placed right after the original in manually sorted albums). Not kept, because PhotoKit has no way to copy them: captions, keywords and people tags added by hand, and shared-album membership. The confirm sheet says so, and adds: "If you use iCloud Shared Library, squished items are moved to your Personal Library and removed for other participants." (PhotoKit cannot tell Shared Library items apart, so squish stays available and discloses this.)
- **Access:** requires full photo-library access. In limited mode album membership can't be read, so squishing is refused until full access is granted.
- **Refused up front:** edited assets, assets with more than one resource (RAW+JPEG, paired video), burst members, Live, animated, Portrait (depth), spatial, slo-mo and cinematic assets, multi-frame images, and items outside the user's own library (shared albums, synced from a computer).
- **Replace flow (two steps, one system prompt):** `prepare` exports the original (the file must decode at the asset's own size), re-encodes, creates the new asset and verifies it as the library stores it: photo size identical, video at the expected (downscaled) size and aspect, exactly one resource of the expected type, stored size and SHA-256 equal to the encoded file, duration within 0.1 s, size at least 20% smaller, audio and timed-metadata tracks, bit depth and colour tags, and favorite, hidden, location, date and albums matching. Each squish is journaled (Store table `squishJournal`) before the library changes, and `reconcile()` settles open rows on launch. `commitDeletes` then re-reads every pair inside the change block and deletes only originals still exactly as verified (an original edited, favorited or re-albumed since is skipped), all in one request (iOS confirms; originals go to Recently Deleted for 30 days). A declined prompt leaves everything in place for retry or discard.
- **Savings are estimates:** space is only freed when Recently Deleted is emptied (or after 30 days), and the UI says so.
- **iCloud-only originals** need a download: shown with a cloud badge, processed on Wi-Fi only, with download progress.
- Free space of at least 2× the item size plus 500 MB is required before each item. Work continues briefly in the background, and stops cleanly when background time expires.

## 9. Device monitor

Read-only gauges, sampled every 1 s while the screen is visible, with a 60-s Swift Charts history:

- **Storage:** total and available (`volumeAvailableCapacityForImportantUsage`), plus Roll's estimate of the photo library size by category.
- **RAM:** `host_statistics64(HOST_VM_INFO64)` (free, active, inactive, wired, compressed pages) against `ProcessInfo.physicalMemory`.
- **CPU:** `host_processor_info` tick deltas → total and per-core load.
- **Thermal:** `ProcessInfo.thermalState`.
- **Battery:** `UIDevice` battery level and state.
- **Uptime:** `ProcessInfo.systemUptime`.
- **Copy rule:** never "boost", "free RAM" or "speed up". ADR-0002 records this for App Review guideline 2.3.
- **Privacy manifest** (`PrivacyInfo.xcprivacy`) declares disk space reason `E174.1` and system boot time reason `35F9.1`. Roll uses no tracking domains.

## 10. Onboarding and paywall

1. Three value screens: "Describe it, Roll finds it" / "Swipe to clean" / "Never leaves your phone".
2. Photos permission (full access recommended; limited access works on the selected set). Then the model download (about 300 MB, with progress, Wi-Fi recommended; meanwhile Vision-only signals start).
3. **Taste scan:** indexes the newest 500 assets, then shows real numbers: "about X GB in screenshots, duplicates, big videos" plus a 6-photo preview of the user's own Screenshots swipefile.
4. **Paywall** (dismissible; free tier per §5):
   - **Annual $29.99 with a 3-day free trial** (preselected, "most popular");
   - **Weekly $4.99, no trial.**
5. **RevenueCat:** entitlement `pro`; products `roll_pro_annual` (3-day free-trial intro offer) and `roll_pro_weekly`, both in one App Store subscription group `Roll Pro`; offering `default`. The paywall is our SwiftUI screen reading `Offerings`, so there's no dashboard dependency.

## 11. Quality

- **Unit tests (Swift Testing)** for Ranking (classifier convergence on synthetic vectors, class balancing, rank-based retrieval under imbalance, exhaustion), Dedupe (grouping on synthetic timestamps and prints), size estimates, Squish metadata preservation (round-trip on fixture files), Monitor parsers (fake Mach structs), free-quota accounting, and Store migrations.
- **Integration:**
  - a simulator seeded with `xcrun simctl addmedia` (the embeddinggemma-coreml fixtures, plus generated duplicates, blurs and screenshots);
  - an XCUITest smoke test for onboarding → taste scan → Screenshots swipefile → swipe 5 → commit (with the delete confirmation accepted) → item count drops;
  - one test that runs the real `GemmaEmbedder` on the simulator (CPU) on 20 fixtures and checks that the Screenshots and Memes prompts rank their fixtures in the top 5.
- **Agent-first repo:**
  - `AGENTS.md` (map, rules, commands); `justfile` (`setup`, `gen`, `build`, `test`, `seed-sim`, `run-device`, `testflight`);
  - `docs/decisions/` ADRs;
  - `STATUS.md` generated by `just status` from the test results and a milestone checklist in `docs/MILESTONES.md`.
- **CI:** GitHub Actions macOS: XcodeGen, build, unit tests.

## 13. Risks

| Risk | Response |
|---|---|
| EmbeddingGemma conversion slips or ends on the GPU fallback | The app ships against the `Embedder` protocol either way. The GPU variant is fine for foreground search; background indexing runs while charging |
| Indexing 50k photos is too slow on old phones | 70-token budget, newest-first, background on power. The taste scan only needs 500 |
| App Review rejects "cleaner" claims | Monitor is read-only and the copy avoids performance claims (ADR-0002). All deletes go through the iOS confirmation |
| The Private preset is sensitive | Face ID gate, no thumbnails in the app switcher (privacy overlay on `scenePhase` inactive), never in notifications |
